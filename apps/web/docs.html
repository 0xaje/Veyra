Product guide / Security model

Recipient verification, explained.

Understand what Veyra checks, how evidence is handled, and where independent confirmation is still required.

01 / Overview

Veyra is a read-only recipient preflight tool for Sui Mainnet. It compares a proposed destination against independently authorized recipient records, when available, and supplements the review with provider-observed blockchain history.

No automatic approval

A transaction's existence is not proof of recipient identity. Veyra does not sign transactions, submit transfers, or determine that an address is safe.

02 / Verification workflow

1. Specify destination

Enter a counterparty identifier and the full Sui address you intend to use.

2. Inspect evidence

Optionally provide a genuine transaction digest for historical context. Memory recall is attempted when configured.

3. Compare records

Remembered addresses must match an exact locally authorized record. Unmatched or conflicting records require review.

4. Independently confirm

Verify address ownership through a trusted channel, particularly if a recipient changes an address.

03 / Evidence sources

Tatum / Sui Mainnet gRPC

Returns real provider-observed transaction information for a supplied digest. A successful response may identify transaction participants and balance changes. It does not independently prove address ownership or the accuracy of a counterparty claim.

Walrus Memory / MemWal

Attempts to recall recipient records. Recalled content is treated as untrusted until it matches a separately maintained local authorization by blob ID and record fingerprint. The current upstream service may return errors; Veyra reports unavailability rather than inventing records.

Local authorization

Exact recipient records can be bound to a blob ID and canonical fingerprint. The current authorization-file mechanism is a local assertion; its integrity and provenance need hardening before production use.

04 / Threat model

Veyra is designed to help surface suspicious recipient changes and address-poisoning lookalikes. It compares full normalized Sui addresses, not just visually similar prefixes and suffixes.

  • A mismatched authorized recipient record must trigger review.
  • A missing or conflicting memory must never count as a match.
  • Blockchain history must never be presented as proof that an intended payee controls an address.
  • Provider outages and malformed evidence must fail closed.

05 / Known limitations

The current implementation is a local prototype, not a production payment security system. It does not independently verify gRPC responses cryptographically, automatically discover a counterparty's true address, or establish the provenance of a local authorization file. Walrus Memory availability depends on an upstream service. No persisted assessment history is provided by the interface yet.
